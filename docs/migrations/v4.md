# v4 Migration Guide

## Release status

This guide covers migration from v3 to v4. Before using v4, confirm that the v4
GitHub tag and Release exist and that the matching npm package is published. Until
then, the published Action remains `Jahrome907/web-quality-gatekeeper@v3` at
v3.2.7; keep existing published v3 workflows unchanged.

## Why this is a major release

v4 removes two unsafe implicit behaviors:

- A visual-enabled audit with missing baselines now fails until a reviewed baseline
  is created explicitly.
- The CLI rejects legacy generated files without an ownership receipt.

The JSON schema URIs and their v1, v2, and PR Risk Ledger schema versions are
unchanged. Existing schema consumers do not need a parser migration.

## Prepare visual baselines

Before enabling a v4 visual gate, review the intended page state and create its
baseline deliberately:

```bash
npx wqg audit https://your-site.example \
  --baseline-dir .github/web-quality/baselines --out artifacts-v4 --set-baseline
```

Review and commit the resulting baseline images. Later visual-enabled runs compare
against those committed files. `--no-fail-on-visual` does not make a missing
baseline an approved baseline. Then rerun the same command without
`--set-baseline` to compare against the reviewed baseline.

## Preserve legacy output safely

The CLI rejects legacy generated files that have no ownership receipt. Keep that
output for history or investigation, and do not attempt to add a receipt to it.
Write the first v4 CLI run to a fresh `--out` directory, for example:

```bash
npx wqg audit https://your-site.example \
  --baseline-dir .github/web-quality/baselines --out artifacts-v4
```

An existing directory with a valid completion receipt remains usable for later
runs. The Action's output directory is fixed at `artifacts/`; do not restore
legacy files there. Take an archival copy outside `artifacts/`, then let the v4
Action create its own output. After a completed Action audit, it exposes upload
paths only from the current invocation's validated receipt. A completed quality
gate may still report a failing audit, but an interrupted or fatal run never
produces an uploadable bundle.

## Update v4 workflow uploads after publication

When the v4 tag is published, use the v4 Action outputs rather than a hard-coded
`artifacts/` path. Require all of the following in the upload condition:

1. `always()` so completed failing audits can still be retained for review.
2. `steps.wqg.outputs.bundle-complete == 'true'`.
3. `steps.wqg.outputs.sensitive-audit == 'false'`, unless the repository has
   intentionally set its existing sensitivity override.

Upload `steps.wqg.outputs.artifact-paths`. A sensitivity override authorizes
handling sensitive output; it never authorizes publication of an incomplete bundle.
The generated v4 scaffold and [v4 consumer example](../../examples/consumer-workflow.yml)
provide the complete workflow form after the tag is available. See the
[changelog](../../CHANGELOG.md) for the selector-timeout, report-navigation, and
offline Python comparison changes.

## Test the source candidate

Before v4 is published, test a source checkout with its built CLI rather than an
unpublished npm version:

```bash
npm ci
npm run build
node dist/cli.js audit https://your-site.example \
  --baseline-dir .github/web-quality/baselines --out artifacts-v4 --set-baseline
```

Review and commit the generated baselines, then rerun the same command without
`--set-baseline`. Use a disposable or deliberately chosen output directory for
that source test.

After the v4 tag and Release exist and the matching npm package is available,
install the released package with:

```bash
npm install --save-dev web-quality-gatekeeper@^4
```
